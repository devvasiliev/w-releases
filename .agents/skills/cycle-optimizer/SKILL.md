# Cycle optimizer

Оптимизируй конкретный цикл работы, сохраняя управление у человека. Не превращай
каждую задачу в постоянную программу улучшений.

В Desktop оператор выбирает Cycle Optimizer из списка `/`. В CLI он открывает
`/skills` либо явно упоминает `$cycle-optimizer`; буквальная команда
`/cycle-optimizer` интерфейсом CLI не поддерживается.

## Старт

1. Установи один код задачи и репозиторий-владелец по `$route-task`.
2. Найди существующее досье командой `task resume`. Если его нет, создай через
   `task init`:
   - класс задачи;
   - 1–4 устойчивых facet пула;
   - критерии хорошо выполненной задачи;
   - scope, non-goals и обязательные проверки.
3. Бери критерии из согласованной задачи, спецификации и прямых требований
   человека. Спроси только о пробеле, который существенно меняет приёмку.
4. Для уже начатой работы укажи `--provenance reconstructed`; неизвестную
   длительность не оценивай и оставляй как `не измерено`.
5. Если оператор задал предел этапа или всей задачи, зафиксируй его в критериях
   качества и создай наблюдаемое событие начала до первой относящейся к этапу
   работы. Время ожидания, реализации, проверки и пауз не смешивай.

Полный контракт команд находится в [task-dossier.md](references/task-dossier.md).

## Выполнение длинной задачи

- Сначала прочитай `contract.md`, `current.md` и последний checkpoint. Они
  являются точкой восстановления после нового чата или сжатия контекста.
- Фиксируй только значимые события: смену этапа, решение, отказ реального
  контура, человеческую корректировку, scope change, проверку и handoff.
- Активный blocker сохраняй до отдельного события `blocker-resolved`; обычное
  следующее событие не означает, что внешнее условие исчезло.
- Создавай checkpoint после законченного смыслового этапа, перед рискованной
  сменой направления и перед handoff. Не создавай checkpoint на каждое сообщение.
- В checkpoint укажи ожидаемое и фактическое состояние, следующий точный шаг,
  blocker, rollback, cleanup и ссылки на evidence.
- Не пытайся определить момент сжатия контекста. Сохраняй состояние на
  смысловых границах, пока оно ещё известно.
- Не сохраняй сырой чат, chain-of-thought, полный лог, credentials, tokens,
  персональные данные или дампы. Оставляй краткий вывод и путь к штатному
  evidence.

## Ограниченный пакет исправлений

1. Перед первой правкой собери полный список замечаний для одного точного
   fingerprint. Сгруппируй проявления по общим причинам и зафиксируй один пакет
   исправлений. Не начинай последовательный цикл по одному замечанию.
2. Замечание валидатора не расширяет scope. Если исправление требует другого
   репозитория, владельца поведения, публичного контракта, топологии, выпуска или
   ранее исключённой работы, останови затронутую часть и покажи оператору:
   причину, добавляемую область, владельца, репозитории, ожидаемое время, риск
   отказа и минимальную альтернативу. До прямого согласования не изменяй
   контракт задачи, код или конфигурацию новой области.
3. Исправь согласованные причины одним пакетом. Correction-check проверяет
   закрытие исходного списка и внесённые регрессии. Новый широкий поиск рисков
   выполняется один раз над готовым fingerprint, а не после каждой локальной
   правки.
4. Порядок тестов задаётся согласованным контрактом задачи. Если оператор требует
   предварительного одобрения, не запускай тестовые команды до него; заранее
   подготовь один точный пакет команд. В обычном режиме запускай локальные
   проверки после пакета, связанные проверки один раз и полный контур только на
   согласованной контрольной границе.
5. После двух отклонённых пакетов либо появления новой категории P0/P1 прекрати
   точечные исправления, верни решение в проектирование и покажи оператору
   причину. Не продолжай неограниченную лестницу correction-check.
6. При достижении временного предела создай checkpoint с фактическим состоянием
   и причиной расхода. Не скрывай превышение продолжением этапа и не объявляй
   гипотезу подтверждённой без измеренного результата.

## Агенты

Используй временных агентов только когда пользователь явно запустил этот skill
и параллельная роль имеет ограниченный результат:

- executor получает одну задачу и конкретный acceptance contract;
- evaluator работает read-only, независимо сверяет результат с contract;
- основной агент остаётся владельцем решений, досье и handoff.

Не создавай постоянного оркестратора и не передавай агенту скрытую обязанность
самостоятельно менять harness. Валидатор консультирует и не разрешает изменение
scope.

## Ретроспектива

Запускай `task review` после результата, отказа handoff или обратной связи
человека. Сопоставь:

- время этапов и блокеров;
- число failures, human corrections и завершённых handoff-попыток;
- качество принятого результата и evidence;
- один доминирующий пробел процесса.

Формулируй проверяемую гипотезу. Отсутствие значимого повторяемого пробела —
нормальный результат; тогда не создавай кандидата.

## Harness-эксперимент

Создавай кандидата, когда существует повторяемый пул задач либо человек явно
хочет проверить процесс на следующей похожей задаче. Следуй
[experiments.md](references/experiments.md).

Обязательные свойства:

- source candidate неизменяем и адресуется `repository:CODE-N:digest`;
- candidate содержит target baseline, точные before/after bytes и digests,
  а также версионированные rubric/evaluation;
- каждая следующая задача пишет evidence только в собственное досье;
- evidence создаётся только после проверки применённого overlay и связывается
  с раздельными target/task changed paths, diff identity и fingerprints;
  same-repository run требует task-only checkpoint до overlay, а полный checkout
  должен быть точным объединением task snapshot и path-filtered target overlay;
  посторонние changes блокируют gate как confounders;
- общий статус вычисляется read-only по зарегистрированным репозиториям;
- exact run не учитывается дважды;
- promotion закрыт до replay, regression, negative, fresh-task и human approval,
  выданного после них для точного digest просмотренного evidence-set;
- failed или rejected candidate становится terminal и исправляется новым digest;
- изменение rules, skills, agents или tooling выполняется отдельной явно
  разрешённой задачей у канонического владельца.

Не продвигай кандидата автоматически. Покажи человеку статус gates, evidence,
оставшиеся риски и минимальное предлагаемое изменение.

## Завершение

Перед handoff создай финальный checkpoint и review. Сообщи:

- результат задачи;
- пройденные и непройденные проверки;
- человеческие корректировки;
- наличие Git drift и целостность dossier;
- статус harness candidate, если эксперимент действительно проводился.

Не объявляй процесс универсальным по одной задаче.
